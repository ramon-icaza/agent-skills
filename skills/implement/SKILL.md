# Скилл `implement` — реализация задачи

## Назначение

Взять задачу (из таск-трекера или из документа `handoff`), разложить её на подзадачи, определить порядок выполнения, поручить подзадачи субагентам, проверить итоговый результат через `review`, при необходимости запланировать исправления и повторить, а в конце выдать пользователю отчёт о проделанной работе.

## Когда применять

- Пользователь передал результат `handoff` (или сформулировал задачу напрямую).
- Нужно реализовать функционал, исправить баг, добавить тесты, рефакторить или иным образом изменить код.

## Общий процесс

### Шаг 0. Получить задачу

Входные данные:
- Результат `handoff` (структурированное задание), либо
- Описание задачи от пользователя, либо
- Задача из таск-трекера (Jira, GitHub Issues, GitLab Issues, Trello и т.д.).

Если задача берётся из таск-трекера, получи её текст, критерии приёмки, связанные комментарии и вложения.

### Шаг 1. Декомпозиция на подзадачи

Разбей задачу на независимые или слабо зависимые подзадачи. Для каждой подзадачи определи:
- **Название и описание.**
- **Тип:** `код` (требуется написание/изменение кода) или `иное` (документация, настройка, анализ, исследование и т.д.).
- **Зависимости:** от каких других подзадач она зависит.
- **Очерёдность:** подзадачи без зависимостей выполняются первыми.

### Шаг 2. Выполнение подзадач субагентами

Для каждой подзадачи вызови отдельного субагента:

- **Если тип = `код`:** субагент использует скилл `tdd` (Red → Green → Review).
- **Если тип = `иное`:** субагент просто выполняет подзадачу согласно её описанию.

Субагенты работают параллельно там, где нет зависимостей, и последовательно — там, где зависимости есть.

### Шаг 3. Проверка результата через review

После того как все субагенты завершили работу по своим подзадачам, вызови субагента со скиллом `review` для проверки всего накопленного результата (всех изменений кода, тестов, документации).

`review` проверяет код по чек-листу скилла `review` (баги, уязвимости, производительность, тесты на опасных местах, компактность diff, YAGNI, отсутствие самописных аналогов stdlib/библиотек).

### Шаг 4. Цикл устранения проблем (если необходимо)

Если `review` выявил проблемы:
1. Агент планирует работы по устранению каждой проблемы (новая декомпозиция или дополнение существующих подзадач).
2. Возвращается к Шагу 1 (дополненная декомпозиция) → Шаг 2 (выполнение исправлений субагентами) → Шаг 3 (повторный review).
3. Цикл повторяется, пока `review` не подтвердит отсутствие критических замечаний.

### Шаг 5. Отчёт пользователю

По завершении всех работ выдай пользователю структурированный отчёт со следующими разделами:

1. **Исходная задача** — краткое описание, откуда взята (таск-трекер, handoff, пользователь).
2. **Выполненные подзадачи** — список с типами, статусом и исполнителями (субагентами).
3. **Изменения** — сводка по изменённым/созданным файлам, краткое описание diff.
4. **Тесты** — какие тесты написаны, сколько проходят, покрытие опасных мест.
5. **Результаты review** — сколько итераций review было, были ли замечания, устранены ли все.
6. **Риски и открытые вопросы** — если есть нерешённые моменты.
7. **Рекомендации по дальнейшим действиям** — что можно сделать следующим.

## Результат

Задача полностью реализована, код прошёл проверку `review`, пользователь получил подробный отчёт.
